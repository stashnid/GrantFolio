# Архітектура першого релізу GrantFolio в Google Cloud

Пропозиція на погодження від 17 листопада 2026 року. Мета — публічний HTTPS-сайт із реєстрацією та підтвердженою роботою для щонайменше 30 одночасно активних користувачів.

Користувач повідомив, що домен уже придбаний у NIC.UA. На скриншоті в кабінеті видно `grantfolio.pp.ua`, строк дії до 17 листопада 2027 року. Користувач просить підключити домен під час майбутнього деплою. DNS-записи ще не змінювалися, право керування DNS під час розгортання слід перевірити.

Користувач також хоче підтверджувати реєстрацію та вхід через email/password одноразовим кодом, який приходить від `grantfoliomanager@gmail.com`. Для Google sign-in окремий код у пошті не потрібен, оскільки особу підтверджує Google OAuth. Вбудоване підтвердження email у Firebase надсилає verification link, тому для запитаного коду потрібен серверний OTP-крок і поштовий відправник з цієї Gmail-адреси. Реалізацію, спосіб доступу до поштової скриньки й обмеження повторної відправки визначити до деплою. Код має бути одноразовим, мати строк дії, обмеження спроб і повторних надсилань; зберігати лише захищене представлення коду. Секрети скриньки не зберігати у Git.

## Сервіси та дані

- Власний домен підключаємо через глобальний зовнішній Application Load Balancer із HTTPS і сертифікатом Google. DNS домену вказує на зарезервовану глобальну IP-адресу балансувальника, а serverless NEG спрямовує запити до Cloud Run. Саме Cloud Run автоматично масштабує інстанси; балансувальник потрібен для входу через власний домен і дає точку для подальшого Cloud Armor/CDN. Cloud Run domain mapping у документації має статус Preview і не рекомендований для production. [Cloud Run custom domains](https://docs.cloud.google.com/run/docs/mapping-custom-domains) · [Cloud Load Balancer з Cloud Run](https://docs.cloud.google.com/load-balancing/docs/https/setup-global-ext-https-serverless)
- Один Cloud Run service віддає React і обслуговує Express API за тим самим власним доменом. Початкова конфігурація — 1 vCPU, 512 MiB, `min=0`, `max=3`, `concurrency=16`. Це стартові параметри для вимірювання. Cold start перевіряємо окремо. Один теплий інстанс розглядаємо за результатами тесту і перевірки витрат. [Cloud Run concurrency](https://docs.cloud.google.com/run/docs/about-concurrency)
- Firebase Authentication обслуговує Google sign-in та email/password із відновленням пароля. Для ручної реєстрації і входу email/password додається окреме підтвердження одноразовим email-кодом від `grantfoliomanager@gmail.com`; сервер перевіряє код, строк дії та ліміт спроб перед видачею доступу. Firebase native email verification — це посилання, тому відправлення коду потребує поштового інтегратора з цієї адреси та секрету в Secret Manager. Google sign-in працює через Google OAuth. Власний домен додається до дозволених доменів Firebase Auth. Express перевіряє Firebase ID token і обмежує приватні операції перевіреним UID. Поштова інтеграція та сам OTP-потік мають бути реалізовані й протестовані перед увімкненням цієї вимоги. Спільну роботу різних вебінстансів забезпечує Cloud SQL for PostgreSQL 17. Пропонуємо однозонний інстанс з автоматичними резервними копіями в тому самому регіоні, попередньо `europe-west1`. Підключення через інтеграцію Cloud SQL без дозволених зовнішніх мереж. Поточний пул має максимум 5 з’єднань на вебінстанс, тож початковий розрахунок для трьох вебінстансів — 15, із додатковим запасом для job, міграцій і переходу між ревізіями. Точний тариф і ліміти БД визначимо за кошторисом і вимірюваннями. [Cloud SQL із Cloud Run](https://docs.cloud.google.com/sql/docs/postgres/connect-run) · [Firebase ID tokens](https://firebase.google.com/docs/auth/admin/verify-id-tokens) · [Firebase email action links](https://firebase.google.com/docs/auth/admin/email-action-links)
- Cloud Scheduler щогодини запускає окремий Cloud Run Job для оновлення грантів. Переносимо наявний CLI в job, вимикаємо таймер у production web і захищаємо запуски від накладання через PostgreSQL. Каталог читає останні збережені перевірки з БД. [Заплановані Cloud Run Jobs](https://docs.cloud.google.com/run/docs/execute/jobs-on-schedule)
- Artifact Registry зберігає образ. Окремий Cloud Run Job застосовує міграції один раз перед випуском вебревізії з того самого digest. Secret Manager зберігає пароль БД та ключ Gemini, якщо асистент увімкнено. Cloud Logging і Monitoring показують затримки, помилки, використання ресурсів і стан оновлення каталогу. [Секрети Cloud Run](https://docs.cloud.google.com/run/docs/configuring/services/secrets)
- Для асистента зберігаємо наявний серверний адаптер Gemini Flash-Lite. Доступ до живої генерації залежить від підтвердженої квоти й покриття витрат. Для запуску з асистентом обмежуємо генерацію за UID і спільною квотою проєкту, зберігаємо доступ до каталогу, профілю й проєктів при відмові провайдера. [Gemini API rate limits](https://ai.google.dev/gemini-api/docs/rate-limits)

## Критерії приймання

30 різних тестових акаунтів працюють одночасно 15 хвилин по HTTPS. Прогін охоплює хвилю входів, перегляд каталогу, читання й збереження профілів, проєктів і бюджетів та TXT-експорт. Для основного API запропоновано p95 до 1 секунди та менше 1% неочікуваних помилок і таймаутів. Усі підтверджені збереження мають читатися повторно, доступ до чужих даних має відхилятися. Окремо перевіряємо старт із нуля, роботу під час оновлення каталогу і пікову хвилю. Заміряємо CPU, пам’ять, SQL-з’єднання та HTTP 429/5xx. Живу генерацію вимірюємо окремо в межах дозволеної квоти, із затримками та відмовами провайдера. Гарантія для 30 одночасних генерацій потребує окремої перевірки квоти й реального тесту.
