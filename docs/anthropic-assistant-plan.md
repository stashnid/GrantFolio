# Claude для GrantFolio: дослідження й план спеціалізації

Дата: 13.11.2026. Статус: рекомендація для пілота, без модельних викликів і витрат. Навчальних матеріалів немає. Остаточний вибір за результатом перевірки на наших кейсах; рекомендація з інтернету сама по собі не доводить перевагу українською.

## Висновок

Пропонуємо перевірити **Claude Sonnet 5.5** як основного автора розділів заявки. **Haiku 5.5** — кандидат для дешевого витягування даних і класифікації після окремої перевірки. Спочатку один Sonnet adapter; автоматичну маршрутизацію між моделями додавати лише після вимірювань. Попередній Gemini-кандидат залишається контрольним варіантом, а не затвердженою моделлю.

Anthropic прямо вказує, що Claude API не пропонує fine-tuning; можливі індивідуальні домовленості потрібно обговорювати з Anthropic. Отже, ми можемо спеціалізувати Claude під наш процес, але не обіцяти доступне SFT його ваг. [Офіційне визначення і обмеження](https://platform.claude.com/docs/en/about-claude/glossary).

## Що означає «під нашого асистента»

| Шар | Наші матеріали й механізм | Результат |
|---|---|---|
| Знання | Чинні правила/форма гранту, URL, дата, сторінка, версія | Актуальні відповіді з джерелами |
| Пам’ять | Підтверджені факти бізнесу та справи в PostgreSQL | Продовження роботи після повернення |
| Стиль | Український редакційний стандарт і перевірені приклади у prompt | Конкретні розділи без вигаданих фактів |
| Дії | Обмежені серверні tools і підтвердження змін | Керований процес підготовки |
| Розрахунки | Єдині формули бюджету в коді | Незмінність підтверджених чисел |
| Якість | Окремі контрольні кейси, людська оцінка, версії | Виявлення регресій перед релізом |

Ці механізми не змінюють ваг Claude. Вони дають практичну спеціалізацію, яку можна перевірити й оновити без нового навчання.

## План від відсутності даних до пілота

1. **Одна програма.** Обрати чинний раунд і офіційну форму. Створити manifest джерел: issuer, URL, checked_at, effective dates, checksum, сторінки/фрагменти. Суперечливі умови перевіряє людина. Результат — погоджена структура одного пакета.
2. **Редакційний стандарт.** Природна українська, конкретні причинні пояснення, збереження сум, видимі припущення, короткі питання при нестачі даних. Підготувати спочатку 15–20 перевірених прикладів на різних бізнес-ситуаціях; 3–5 релевантних прикладів подавати в prompt. Ці числа — наш початковий орієнтир, не вимога провайдера.
3. **Окремі контрольні кейси.** До налаштування prompt відкласти 20–30 інших кейсів: повні дані, пропуски, суперечності, зміна ціни, застаріла умова, інструкція всередині документа. Всі варіації одного бізнес-кейсу тримати в одному наборі. Тестові відповіді не підкладати у prompt.
4. **Контекст.** Backend спершу перевіряє owner/case, потім дістає потрібні приватні факти та релевантні офіційні фрагменти. Для одного гранту достатньо SQL/секцій документів. Загальний каталог і приватні файли мають різні області доступу. Unknown передається явно.
5. **Workflow.** Intake → перевірка відсутніх фактів → пропозиція → підтвердження → чернетка → перевірки → export snapshot. Інструменти: читати свою справу/умови, порахувати бюджет, запропонувати patch, запросити експорт. Модель не має довільного SQL/файлового доступу і не подає заявку самостійно.
6. **Перевірка.** На однаковому context порівняти Sonnet і попереднього Gemini-кандидата за фактичною опорою, мовою, повнотою, уточненнями, токенами/вартістю й часом. Haiku перевірити окремо на extraction. Людина оцінює відповіді без назви моделі; модель-суддя не замінює перевірку фактів.
7. **Пілот.** Один обмежений погоджений запуск; відсутні критичні вигадані факти/суми та витік між користувачами, усі механічні перевірки проходять. Менші стилістичні недоліки записуються. Реальні користувачі переглядають результат перед використанням; збираємо відгуки й виправлення.
8. **Версії.** Зберігати model/endpoint, prompt, source manifest, test version, результат і release decision. Регресія → повернення попередньої конфігурації. Виправлення користувача не стає автоматично правильною навчальною відповіддю.

Реальні заявки беруться лише з дозволом на відповідне використання. Для старту придатні явно вигадані бізнес-ситуації з перевіреними людьми відповідями. Правила програми залишаються справжніми. Повні приватні дані не комітяться.

## Якщо потрібне саме донавчання ваг

Варіант A: індивідуальний доступ Anthropic — тільки після письмового підтвердження доступного model ID, методу, умов даних, експорту/serving, мінімального обсягу та ціни. Звернення компанії в цій задачі не надсилалося; позитивної відповіді немає.

Варіант B: якщо такого доступу немає, залишаємо Claude із описаною спеціалізацією або окремо обираємо trainable основу, наприклад Gemini з managed SFT. Підготувати 100–200 якісних перевірених train-прикладів плюс окремі validation/test; це плановий орієнтир. Вузька задача — написання розділу з фактів або уточнення missing facts. Спочатку baseline, потім один training job, однаковий holdout і рішення про реліз. [Попередній SFT-план](ai-training-plan.md).

Не переносимо гарантію донавчання з іншої моделі/платформи на актуальний Sonnet. Історичні партнерські винятки потребують перевірки точного продукту й поточного доступу.

## Хто робить роботу

Astra узгоджує scope і приймання; Sol перевіряє джерела/дані; Terra реалізує adapter, workflow й тести. Окремий агент перевіряє зміни доступу та розрахунків. Обидва учасники використовують Codex, звіти/рішення передаються GitHub. [Протокол роботи](codex-collaboration.md).

До демо пріоритет — робочий HTTPS-сценарій і справжні відгуки. Реальне SFT не оголошується завершеним або обов’язковим для оцінювання.
