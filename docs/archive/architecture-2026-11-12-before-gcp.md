## 1. Що повинно працювати до демо

Вимоги викладача:

- Реальні верхньорівневі частини backend/, frontend/, infra/ та README.md з описом, запуском і розгортанням: 3 бали.
- Прототип через HTTPS, у якому можна зареєструватися та увійти: 3 бали.
- PDF-звіт: кому показали продукт, скільки людей спробували, що сказали та що змінилося після цього: 4 бали.
- Оплата або пожертва від користувача з доказами: необов’язковий бонус.
- Кожен учасник подає посилання на репозиторій, URL демо та звіт.

Продуктовий сценарій: реєстрація -> опис бізнесу -> підтверджений профіль -> пояснений підбір -> справа для однієї підтримуваної програми -> документ і підтвердження прочитаних даних -> бюджет і текст -> зміна ціни -> узгоджений оновлений експорт -> повернення до збереженої справи.

Каталог може містити кілька перевірених можливостей. Повну підготовку підтримуємо для однієї програми; для решти явно показуємо доступні можливості. Конкретну програму та її офіційні форми потрібно обрати й перевірити першими. Загальний PDF із довільним текстом не вважаємо готовим офіційним пакетом.

Моніторинг і поштову підписку з README плануємо як вузьку працюючу реалізацію: 1–2 перевірені джерела, видимий час перевірки, реальна доставка листа. Широке покриття потребує наступних ітерацій. Зміна погодженого продуктового обсягу обговорюється окремо, а незавершені функції позначаються чесно.

## 2. Рекомендований стек

| Частина | Пропозиція | Навіщо |
|---|---|---|
| Інтерфейс | React + Vite + TypeScript | Чат, каталог, профіль, справа, форми та перегляд змін |
| Сервер | Node.js + Express + TypeScript | Доступ до даних, підбір, бюджет, ШІ, файли, перевірки, експорт |
| Облікові записи | Supabase Auth | Реєстрація, вхід, підтвердження пошти, відновлення доступу |
| Дані | PostgreSQL у Supabase | Профілі, справи, історія, правила, бюджети та статуси |
| Файли | Приватне Supabase Storage | Оригінали документів і результати експорту |
| ШІ | Серверний адаптер; кандидат OpenAI Responses API | Діалог, витяг даних і тексти з типізованою структурою |
| Пошта | Один SMTP/транзакційний провайдер; кандидат Resend | Листи реєстрації та підписки, після перевірки відправника |
| Розгортання | Один Docker web service у Render | Інтерфейс і /api на одному HTTPS-домені |
| Розклад | Один Render cron job із командою backend | Перевірка джерел і поштові добірки незалежно від відкритого браузера |
| Автоматичні перевірки | GitHub Actions | Збірка, перевірка типів і тести ключової поведінки |

Назви постачальників є рекомендаціями. Акаунти, доступні моделі, тарифи й бюджет ще не підтверджено. Версії Node та залежностей фіксуємо в реалізації за поточною сумісністю, разом із lockfile.

Чому один TypeScript-стек: одна мова на клієнті й сервері, простіше узгоджувати дані, один процес розгортання. Якщо команда суттєво краще знає Python або обраний документ вимагає конкретного Python-інструмента, прийнятна альтернатива — FastAPI замість Express; решта схеми зберігається. Зараз таких обмежень не встановлено.

## 3. Схема системи

```text
Браузер: React
  |-- реєстрація / вхід ----------------------> Supabase Auth
  |
  +-- HTTPS /api + токен користувача
       |
       v
  Express: один модульний сервер
    |-- профіль, каталог, справи, чат
    |-- правила підбору і розрахунки бюджету
    |-- документи, пропозиції змін, тексти, експорт
    |-- перевірка власника даних і ліміти запитів
    |
    +--> PostgreSQL через приватні repositories: стан продукту і версії
    +--> Private Storage: документи й експорти
    +--> AI API: тільки потрібний контекст
    +--> Поштова служба

  Render cron: та сама кодова база, коротка команда
    +--> перевірені джерела -> кандидати змін -> перевірка -> каталог
    +--> підбір нових можливостей -> черга листів -> доставка
```

Frontend і backend мають окремі каталоги, але production-збірка інтерфейсу обслуговується сервером. Це зменшує кількість налаштувань доменів і доступу між ними. На старті потрібні один web service і одна запланована команда, а не набір незалежних мікросервісів.

## 4. Організація репозиторію

Запланована структура, яку ще потрібно реалізувати:

```text
backend/
  src/
    bootstrap.ts     # з’єднання реалізацій і запуск
    modules/
      business/      # підтверджений профіль
      grants/        # джерела, каталог, правила підбору
      applications/  # справи, документи, бюджет, тексти й експорт
      assistant/     # розмова, пропозиції, обмежений workflow ШІ
      notifications/ # підписки й доставка
    infrastructure/  # підключення БД, auth, AI/storage/mail adapters
  tests/
frontend/
  src/
    pages/
    components/
    features/
    api/
infra/
  Dockerfile
  .dockerignore
  README.md          # bootstrap, секрети, ручні передумови й порядок deploy
  render.yaml
  supabase/
    config.toml
    migrations/
    seed.sql
.github/workflows/ci.yml
.env.example
package.json
package-lock.json
README.md
docs/
  architecture.md
  planning/          # звіти агентів, допоміжні матеріали
```

У кожному модулі лише потрібні файли: public.ts (публічні функції та DTO), http.ts/schemas.ts (API), service.ts/domain.ts/ports.ts (правила й власні інтерфейси), repository.ts (SQL та відображення рядків). Не створюємо порожні шари лише для вигляду.

Між модулями дозволені тільки оголошені public.ts, без імпорту сусіднього repository чи запитів до його таблиць. Граф залежностей: business та grants незалежні; applications викликає їхні public-контракти; assistant використовує ці три контракти; notifications отримує DTO через business/grants. Шари всередині: API -> бізнес-сервіс -> порт збереження; конкретні adapters під’єднуються у bootstrap. Бізнес-сервіс не імпортує Express, pg або SDK ШІ. Перевірка залежностей у CI має відхиляти заборонений імпорт, включно з aliases.

Одна історія SQL-міграцій у infra/. У backend/ — реальна логіка продукту, у frontend/ — взаємодія з користувачем. README зберігає опис продукту та отримує фактичні перевірені інструкції після реалізації. Запропоновані npm-команди не видаємо за вже працюючі.

## 5. Дані та право доступу

Основні сутності:

| Сутність | Що зберігає |
|---|---|
| businesses | Власника, підтверджений профіль, поточну версію |
| grant_rounds | Програму/раунд, джерела, статус, дедлайн, версію правил і шаблону |
| application_cases | Власника, бізнес, обраний раунд, версію справи та підтверджені факти |
| messages | Історію чату й ідентифікатори повторюваних запитів |
| documents | Приватний ключ файлу, тип, hash, витягнуті пропозиції та посилання на сторінки |
| budget_lines | Позиції, кількість, точну ціну, валюту, підтвердження |
| draft_versions | Незмінний знімок тексту, бюджету, версій правил і файлів експорту |
| operations | Стан операцій ШІ/витягу/експорту та захист від дублювання |
| sources, ingestion_runs | Дозволені джерела, результати перевірок і помилки |
| subscriptions, notification_outbox | Налаштування підписки, чергу листів і підтвердження доставки |
| feedback | Відгук, пов’язану версію застосунку й дані для звіту |

Пропозиції фактів можуть спочатку бути структурованими полями документа/повідомлення; для невеликої версії не потрібно окремої таблиці на кожен тип факту. Ідентифікатори програми й раунду відрізняються. Новий раунд і продовження дедлайну обробляються по-різному.

Підтверджений факт має значення, походження, час підтвердження та посилання на документ/сторінку або відповідь користувача. Сума зберігається в копійках або точному decimal, кількість — із визначеною точністю; для першої справи одна валюта. Час у БД — UTC, у UI — потрібний користувачу часовий пояс. Дедлайн без часу не перетворюємо на вигадану точну мить.

Кожен модуль володіє своїми таблицями в окремій схемі: business, grants, applications, assistant, notifications. Справи, документи, бюджет і знімки експорту належать applications: їхня критична зміна залишається однією транзакцією. Дані профілю та вимоги програми копіюються у справу через публічні контракти як версійовані знімки; repository заявок не робить прихованих joins із чужими модулями.

Supabase відповідає за паролі й сесії. Сервер перевіряє підпис, строк дії та належність токена, формує Actor із перевіреної особи. user_id, права й внутрішні статуси з тіла запиту не приймаються як достовірні.

Після звірки з Module 4 пропонуємо змінити попередній REST/RPC-варіант збереження: приватні дані продукту доступні через backend-only PostgreSQL repository та Unit of Work — об’єкт, який об’єднує кроки use case в одну транзакцію. Окрема роль app_runtime не є власником БД і не має BYPASSRLS. Міграції мають окремі повноваження. Приватні схеми не відкриваються браузеру через Data API; прямі записи browser-ролей закриті.

На одному позиченому DB-з’єднанні repository починає транзакцію та задає перевірений Actor як локальний для транзакції параметр. RLS (правила доступу до кожного рядка) використовує його для обмеження власником. Відсутній Actor дає відмову. Значення не береться напряму з request JSON і не залишається сесійним налаштуванням на pooled connection. Окремо перевіряємо повторне використання з’єднання між двома користувачами. Цей адаптер потрібно випробувати на реальному Supabase під час першого технічного запуску; сам факт підключення до Postgres не означає, що RLS працює.

ApplicationsService володіє перевірками й єдиною точною формулою бюджету у звичайному TypeScript. Під час зміни він у Unit of Work завантажує власну справу з блокуванням/версією, перевіряє підтвердження, обчислює результат, зберігає зміни й результат команди та завершує транзакцію. PostgreSQL відповідає за атомарність, базові constraints і контроль версій; формули гранту не дублюються в SQL. Так можна перевіряти правила без HTTP й зовнішньої БД, як у лекції.

Експорт створює незмінний авторизований знімок тексту, фактів, бюджету та версій. Зовнішні виклики ШІ/Storage/генератора виконуються після завершення транзакції; row locks не тримаємо під час мережевого очікування. Повільний результат не може замінити новішу справу.

Це явна зміна рекомендації до реалізації, а не вже проведена міграція. Її ціна — налаштування окремої DB-ролі й перевірка actor context. Якщо обираємо REST/RPC, повертаємося до альтернативи у звіті агента з чесним обліком повноважень і правил, а не підтримуємо дві паралельні моделі доступу.

Файли зберігаються в приватному Storage. Доступ до кожної операції й короткочасного підписаного посилання перевіряє backend; шляхи/Storage policies не дають іншому користувачу доступу. Привілейовані DB/Storage/API ключі не потрапляють у браузер.

## 6. Робота асистента

На кожному кроці сервер:

1. Авторизує користувача та зберігає повідомлення з унікальним request_id.
2. Збирає підтверджений профіль, поточну справу, версію правил, відкриті питання й потрібні уривки документів.
3. Передає обмежений контекст до ШІ.
4. Для чату передає текст поступово (streaming), а підсумкові структуровані зміни отримує за схемою: текст, питання, запропоновані факти, джерела, наступна дія.
5. Перевіряє структуру, допустимі поля, дійсність посилань і право доступу.
6. Показує пропозиції користувачу. Зміна підтверджених даних потребує його явної дії.

Історія та факти зберігаються в нашій БД, тому повернення користувача не залежить від пам’яті зовнішньої моделі. Коротке резюме чату лише скорочує контекст.

ШІ пояснює умови, уточнює запит, витягує кандидатні значення і готує тексти. Код рахує бюджет, перевіряє формальні критерії, власника й комплектність. Невідомий критерій підбору повертається як «потрібно уточнити», з конкретним питанням. Вигаданий відсоток шансів не використовується.

Операції асистента обмежені: отримати контекст справи, підібрати програми, запропонувати зміну, розрахувати бюджет, підготувати розділ. Модель не отримує довільний SQL, команди комп’ютера, довільні URL чи можливість самостійно надсилати листи. Текст файлів і сайтів залишається даними; інструкції всередині цих матеріалів не змінюють правила системи.

Промпти зберігаємо файлами у Git. Запис операції містить prompt_version, model, input_hash, case_revision, tokens, latency та outcome. Зміна промпту або моделі перевіряється на представницьких прикладах за властивостями: правильні факти, явні невідомі дані, коректна схема й джерела. Точний збіг згенерованого тексту не є критерієм. Розмір набору прикладів із лекції та платний ШІ-суддя не стають додатковими вимогами здачі.

Починаємо з інструкцій, якісних прикладів українських текстів і перевірок результату. Окреме навчання моделі, векторна БД та кілька автономних агентів усередині продукту зараз не потрібні. Це не стосується агентів розробки, які допомагають команді.

## 7. Документи, бюджет і експорт

Вхідний шлях: перевірка типу/розміру -> приватне збереження оригіналу -> витяг -> кандидатні факти з посиланнями -> підтвердження -> нова версія справи.

Стартові формати пропонуємо обмежити невеликими PDF, JPEG/PNG, потрібними для обраного сценарію. Ліміти й якість витягу перевіряємо на реальних зразках у перший день інтеграції. Нечитабельний або захищений файл дає зрозумілу помилку й можливість уточнити дані вручну. Перевірка змісту не підтверджує справжність довідки.

Ключовий сценарій зміни ціни:

```text
новий документ/ціна
  -> пропозиція з джерелом
  -> підтвердження користувача + expectedRevision
  -> атомарна зміна фактів, бюджету й версії справи
  -> залежні тексти потребують оновлення
  -> нові тексти + перегляд користувачем
  -> новий знімок та експорт
```

Якщо два вікна змінюють одну версію, друге отримує конфлікт і оновлює дані. Експорт прив’язаний до незмінного знімка: текст, бюджет, case_revision та requirement_version. Зміна справи під час генерації не перетворює старий файл на поточний. Подані пакети не перезаписуються.

PDF/XLSX або інші потрібні формати створюються шаблонами й кодом. Формати та обов’язкові додатки визначаються перевіреними документами саме обраної програми. Статус «готово» потребує відсутності обов’язкових прогалин і перегляду користувачем. Чернетку можна експортувати з явним переліком незавершеного.

## 8. Короткий запит, потоковий чат і збережене завдання

Після Module 6, стор. 5 і 21, уточнюємо початкову рекомендацію: вміститися у довгий timeout хостингу недостатньо для зручного сценарію.

- Коротка класифікація/невеликий результат за кілька секунд: обмежений синхронний запит.
- Чат, який користувач читає під час відповіді: streaming, наприклад SSE, з видимим станом очікування.
- Витяг/генерація на десятки секунд, пакети й робота з повторами: 202 + збережене завдання + виконавець + перегляд статусу.

На початку інтеграції вимірюємо реальні приклади документів. Для повільного сценарію відразу потрібна Postgres-черга operations: атомарне захоплення, обмежена оренда, відновлення після перезапуску, перевірка input/case_revision і обмеження спроб. API й worker використовують ті самі бізнес-сервіси й можуть постачатися одним образом із різними командами запуску. Окрема платформа черг для цього прототипу не потрібна.

Якщо всі підтримувані операції справді короткі, worker не додаємо. Платний постійний процес не вважається погодженим. Тривала синхронна обробка могла б бути лише явним тимчасовим спрощенням із прийнятими обмеженнями, а не висновком, що вона рекомендована курсом.

Для кожної операції обов’язкові запис стану перед викликом провайдера, timeout/abort, перевірка версії перед збереженням, request_id і відсутність повторного застосування ефекту. База може запобігти дублю результату, але не гарантує, що невизначений мережевий повтор не буде ще одним оплачуваним викликом моделі. Перервана операція має чесний статус і можливість повтору. 202 без збереженого завдання й лише promise у пам’яті не є надійним фоном.

Моніторинг джерел запускається окремою короткою запланованою командою. Реалізація streaming/job не змінює перевірку власника й не дозволяє моделі самій підтверджувати факти.

## 9. Моніторинг і пошта

Початкова база — перевірені записи та 1–2 справді доступні джерела. Підключення конкретних сайтів/API ще не випробувано. Для кожного джерела зберігаємо адресу, спосіб читання, інтервал, час останньої успішної спроби, hash і помилку.

Запропонований інтервал — 30–60 хвилин. Команда перевіряє дозволені адреси, збирає зміни, об’єднує дублікати й формує кандидатів для публікації. Критичні витягнуті умови перевіряє команда перед використанням у правилах підбору. Якщо джерело недоступне, останні підтверджені дані зберігаються із датою перевірки.

Відправлення листів відбувається лише за активною підпискою і перевіреним статусом раунду. Запис перевіреного нового раунду та обов’язкової події доставки зберігаються узгоджено: для надійного handoff потрібен transaction outbox або повторюване сканування опублікованих версій із checkpoint. Outbox події публікації належить grants і створюється в його транзакції; notifications ідемпотентно приймає DTO події через публічний контракт і створює власні записи доставки. Конкретний міжмодульний контракт grants -> notifications передає тільки DTO; не робимо неявні записи у чужі таблиці. Унікальний ключ user/round/type у БД запобігає повторній добірці. Після відписки вже поставлені листи також не надсилаються. Зміна дедлайну — окремий тип повідомлення, а не новий грант. Зберігаємо результат доставки, без вмісту приватних документів у журналах.

Render cron — рекомендований керований запуск, що потребує погодженого бюджету. Якщо потрібен безплатний варіант, GitHub Actions schedule може запускати ту саму команду, але за документацією можливі затримки й пропуски. Це буде явно описаний режим прототипу без гарантії точного інтервалу. Жоден варіант не означає охоплення всіх грантів інтернету.

## 10. API та перевірки поведінки

Основні групи API:

- /api/businesses: профіль і підтверджені зміни;
- /api/grants та /match: каталог і пояснення відповідності;
- /api/cases: справа, повідомлення й пропозиції змін;
- /api/cases/:id/documents: завантаження та результати витягу;
- /api/cases/:id/budget та /checks: бюджет і виявлені проблеми;
- /api/cases/:id/exports: створення результату з поточної версії;
- /api/operations/:id: авторизований стан довгої/перерваної операції та відновлення UI;
- /api/subscription і /api/feedback: підписка та відгук;
- /healthz та /readyz: стан процесу й готовність сервісу.

Схеми запитів і відповідей узгоджуємо до паралельної реалізації. Зміни приймають expectedRevision та ключ команди; помилки мають code, message, requestId. Приватний запис іншого користувача не розкриває його існування. Підтримуємо зрозумілі стани протермінованої сесії, конфлікту версій, великого файлу, ліміту запитів та недоступного провайдера.

Перевірки перед запрошенням користувачів:

1. Нова зовнішня адреса: signup, підтвердження, signin, reload, logout, повторний вхід.
2. Користувач B не може прочитати/змінити справу A чи завантажити її файл через підміну ID.
3. Відомий приклад бюджету: точні підсумки, власний внесок і зміна ціни; конфлікт двох вкладок.
4. Витяг помилкової суми не змінює факт до підтвердження; відсутня інформація залишається невідомою.
5. Після зміни даних старий експорт не позначається поточним; новий містить узгоджений текст і числа.
6. Помилка ШІ/перезапуск/повтор не втрачають введення та не створюють дубль.
7. Повторне оголошення не дублює раунд або лист; закритий раунд і відписаний користувач не потрапляють у розсилку.
8. Перевірка імпортів відхиляє звернення до чужих internals; сервіс бюджету тестується без HTTP/БД; реальна DB-роль відхиляє відсутній/чужий Actor і не змішує користувачів у pool.
9. Чистий клон запускається за README; HTTPS-демо працює з нового браузера; перевірено повернення попередньої версії.

Автоматизуємо розрахунки, правила, доступ та повторювані команди. Окремо перевіряємо реальний signup, доставку листів, читабельність експорту й увесь шлях на розгорнутому застосунку. Зімітуваний API в тесті не є доказом роботи зовнішньої інтеграції.

## 11. Розгортання та локальна робота

Локально плануємо npm workspaces, один lockfile, Supabase CLI/Docker для локальної БД/Auth/Storage, неперсональні seed-дані та .env.example. Vite передає /api локальному Express. Зовнішня модель вмикається серверним ключем; для автоматичних тестів допускається явний тестовий адаптер.

У production Docker збирає обидві частини, а Node віддає інтерфейс і API через PORT на 0.0.0.0. Render дає HTTPS-адресу; власний домен для демо не обов’язковий. Налаштовуємо точні callback URL для підтвердження пошти й відновлення пароля. Ключі ШІ, пошти та привілейованого доступу — тільки в серверному середовищі, не у VITE_*.

Два перевірені обмеження потрібно врахувати одразу:

- Типова пошта Supabase Auth обмежена адресами команди й не підходить для зовнішніх тестувальників. Рекомендація — власний SMTP та перевірка доставки до запрошень.
- Render Free засинає після 15 хвилин без трафіку, а пробудження може займати близько хвилини. Постійні дані й файли не зберігаємо на його локальному диску. Для надійного показу рекомендуємо активний тариф на період тестування/демо, після погодження витрат. Безплатний режим описуємо з його обмеженнями.

До реалізації не створюємо платних ресурсів. Статті витрат: web hosting, scheduler, SMTP/транзакційна пошта, AI API; використання БД/Storage залежить від тарифів і лімітів. Конкретний бюджет ще не встановлено. Потрібні ліміти запитів і розміру файлів, контроль витрат за операціями.

Dockerfile описує контейнер, але не всю інфраструктуру. infra/README.md має зіставляти кожен зовнішній блок із конфігурацією або точною ручною передумовою: Supabase project/Auth/redirects, Storage, SMTP, scheduler і секрети. Terraform — можливий інструмент після перевірки реальних providers, а не вимога наданого завдання й не порожня папка для вигляду. Для прототипу достатньо local + одне demo-середовище. Другий учасник перевіряє запуск і розгортання з чистого clone.

До демо зберігаємо захищений експорт БД та окрему копію потрібних об’єктів Storage. Відкат коду не є відкатом даних. Міграції переважно додавальні, із перевіркою сумісності. Демо має залишатися доступним для перевірки після показу, з урахуванням можливого призупинення безплатних проєктів.

Для кожної сесії достатньо записати: хто/роль, дата, завдання, що вийшло, що сказали, яка зміна зроблена й чи перевірена повторно. Особисті дані та бізнес-документи не публікуємо без погодження учасника. Оплата/пожертва необов’язкова; докази мають належати реальним користувацьким спробам. Платіжний модуль не витісняє основні критерії.

## 13. Паралельна робота команди

Запропоновано два напрями; імена не призначено без узгодження:

- A: інтерфейс, signup/login, чат, каталог, справа, підтвердження змін, спостереження за користувачами.
- B: міграції/права, API, правила, ШІ/файли, експорт та розгортання.

Спочатку спільно фіксуємо схеми й один контрольний приклад. Щодня інтегруємо завершений шлях у доступне демо. Не залишаємо поєднання окремих частин на 18 листопада.

Наступні агенти реалізації можуть отримати окремі ділянки лише після вибору стеку та конкретного сценарію. Зміни прав доступу й центральний сценарій перерахунку перевіряємо перехресно.

## 14. Залежності до першого запуску

- Вибрати конкретну програму, чинний раунд, офіційні шаблони та вимоги до експорту.
- Перевірити акаунти для хостингу, БД/Auth/Storage, ШІ, пошти та доступні ліміти; погодити витрати.
- Перевірити відправника/домен пошти або обрати інший явний спосіб входу; не вимикати підтвердження непомітно.
- Визначити 1–2 робочі джерела моніторингу та вручну підтвердити початковий каталог.
- Домовитися з реальними тестувальниками на 16–17 листопада.
- Визначити доступ викладача до приватного репозиторію: надати доступ або окремо погодити публічність після перевірки вмісту.

Подальші етапи з README зберігаються: більше програм/форм, репетиція співбесіди, листи після подання, супровід до виплати та зобов’язання після фінансування. Вони не оголошуються додатковими вимогами навчального звіту.
