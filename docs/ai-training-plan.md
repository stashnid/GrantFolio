# План донавчання асистента

Стан на 12.11.2026: **матеріалів немає, набір не створений, модель не донавчена**. Попередня основа — `gemini-3.5-flash-lite`; вибір залежить від доступу й перевірки якості. Це продуктова робота, а не додатковий критерій викладача.

## Що будемо навчати

Перше вузьке завдання: **підтверджені факти бізнесу + вимоги розділу → якісна українська чернетка або короткі запитання про відсутні дані**. Потрібні природна мова, конкретна аргументація, збереження чисел і відмова вигадувати показники.

Розділяємо три механізми: prompt задає роль/формат; retrieval дає актуальні джерела; supervised fine-tuning змінює параметри готової моделі на перевірених input/output прикладах. Профіль користувача й дедлайни не стають навчальною пам'яттю. Не тренуємо модель з нуля.

## Етап 1. Отримати матеріали

1. Обрати першу програму й чинну офіційну форму, описати структуру відповіді та короткий український редакційний стандарт.
2. Зібрати дозволені зразки від грантових фахівців/авторів або підготувати навчальні ситуації з явно позначеними вигаданими бізнес-даними. Публічний доступ до заявки сам по собі не дає права навчання.
3. Для кожного target людина перевіряє всі твердження, числа й вимоги. ШІ може допомогти з чернеткою; автоматичне схвалення власних відповідей не є перевіреною розміткою.
4. Реальні приватні заявки використовувати лише з дозволом саме на навчання й після очищення персональних/конфіденційних відомостей. Згода на тест продукту не є згодою на SFT.

Офіційні правила й шаблон без якісної цільової відповіді — корпус знань, а не готовий train-набір.

## Етап 2. Розмітити й розділити

Для кожного прикладу потрібні case/group ID, тип задачі, вхідні підтверджені факти/unknown, source excerpts, target response, походження/права, reviewer і версія стандарту. Типи: повні факти; відсутні факти; суперечність; перефразування без нових тверджень.

Робочий орієнтир — 100–200 перевірених train-прикладів для однієї задачі плюс окремі validation/test. Це пропозиція обсягу, не гарантія якості або вимога завдання. Google радить починати приблизно зі 100 якісних прикладів. [Підготовка даних](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/tuning/supervised-tuning/prepare-data).

Поділ робимо за бізнес-кейсом/родиною документів до перефразувань. Усі похідні одного кейсу лишаються в одній групі. Validation допомагає налаштувати процес; test не використовуємо для редагування прикладів чи prompt. Менший набір може перевірити технічний pipeline, але не доводить якість продукту.

Повні дані — у приватному storage. У Git — стандарт, схема, код перевірки, manifest версії/хешів/прав і лише дозволені знеособлені приклади. Дані користувачів і secrets не комітяться.

## Етап 3. Базовий результат і запуск

Спочатку на зафіксованих кейсах перевірити base + prompt + той самий source context. Зафіксувати повторюваний недолік, який хочемо виправити SFT. Зібрати людські виправлення в train-набір; не підганяти train під прихований test.

Google Cloud managed SFT підтримує обрану основу. Для Gemini 3 навчання використовує `us`/`eu` multi-region endpoints; tuned serving — `us`/`eu`/`global`. Для нашого плану розглядаємо `eu`, перевіривши доступ. На tuned задачах Google рекомендує minimal thinking. Controlled generation після tuning потребує окремої перевірки якості/сумісності. [Підтримка й обмеження SFT](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/tuning/supervised-tuning).

Текстовий dataset — JSONL у private Cloud Storage, з `systemInstruction` та `contents` user/model. Перевірити структуру, довжини, unknown, дублікати й відсутність приватних даних. [Формат text tuning](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/tuning/text). Gemini API в AI Studio зараз не має відповідного fine-tuning шляху; потрібен managed Google Cloud SFT. [AI Studio tuning](https://aistudio.google.com/docs/model-tuning).

Перед одним пілотним training job перевірити funding gate з [дослідження](ai-model-research.md), порахувати токени × епохи, inference/evaluation/storage, визначити ліміт і отримати дозвіл на конкретні витрати. Цей документ не запускає й не дозволяє платне навчання.

## Етап 4. Порівняти й випустити

Порівнюємо base і tuned на однакових недоторканих input/context. Людина оцінює фактичну опору, відсутність вигаданих чисел/гарантій, доречність уточнень, повноту й українську мову. Код перевіряє схему, джерела та незмінність підтверджених сум. Окремо записуємо latency/tokens/cost.

Реліз можливий після покращення погодженого недоліку без критичних регресій. Інакше лишаємо base й описуємо результат чесно. Невелика перевірка не є доказом універсальної переваги чи відсутності hallucinations.

Manifest експерименту зберігає dataset/split versions, base ID, prompt/schema version, hyperparameters, job ID, результати, рішення та посилання на приватний tuned endpoint config. Перемикання base/tuned через adapter забезпечує rollback. Після змін програми оновлюємо джерела й правила, а не автоматично запускаємо нове навчання.

До демо пріоритет — робочий корисний сценарій і фактичні відгуки. SFT включаємо лише за готових даних, доступу й перевіреного результату; його відсутність не підмінюємо словами «ми навчили prompt».
