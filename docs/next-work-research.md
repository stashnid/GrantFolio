# Наступна робота: дослідження й план виконання

13.11.2026. База: 44dc3fe, fresh fetch успішний, нових командних змін немає. Це уточнення порядку реалізації; коду, cloud deployment, benchmark і реальних user trials ще немає. Дати нижче — планові цілі, не гарантія готовності. Доступні години команди не встановлено.

## Що змінило дослідження

1. Перший технічний ризик — не вибір LLM, а невизначені чинна програма, раунд і формат результату. Без цього неможливо правильно спроєктувати поля, формули та експорт.
2. Повна архітектура з worker/outbox/storage/monitoring/email має впроваджуватися вертикальними зрізами. Одночасне створення всіх компонентів затримує перший корисний сценарій і перевірку реальними людьми.
3. Вибір Opus залишається кандидатом. Невелика перевірка критичних помилок потрібна перед користувачами; повне порівняння 24 кейсів не повинно блокувати реалізацію входу й збереження справи.
4. GitHub PR із планами ще не об’єднано в main. Перед роботою другого учасника потрібно явно погодити спільну базу; одного git pull main зараз недостатньо для отримання найновіших рішень.

## Перша програма: предметна рекомендація

Пропоную першим адаптером напрям започаткування бізнесу оновленої «Власної справи». Це рекомендація для обговорення з командою, не остаточний вибір. [Поточна сторінка Дії](https://diia.gov.ua/services/zapochatkuvannia-ta-masshtabuvannia-vlasnoi-spravy/) дає опис, інструкцію подання та посилання на приклад бізнес-плану; для подання зазначено PDF. Приклад є матеріалом для перевірки структури, а не автоматичним доказом чинності всіх його полів.

Під час відкриття 13.11 сторінка показала завершення етапу 27.10.2026, тоді як пошукова копія містила інше формулювання про початок. Тому поточний відкритий набір **не підтверджено**. Наявність кнопки «Подати заявку» цього не доводить. До перевірки нового раунду картка має статус needs_review, а не open. Підготовку демонстраційної чернетки можна показати чесно, без обіцянки чинного прийому.

У [вересневому повідомленні Дії](https://diia.gov.ua/news/vlasna-sprava-zbilshyly-hranty-na-start-i-masshtabuvannia-biznesu) описано оновлення програми. Отже, старі суми/вимоги з навчальних статей не переносимо в код. Повне нормативне звірення й перевірку поточної форми ще треба виконати; юридичні правила тут не затверджуються.

Результат B01: source manifest, перевірена форма, карта «поле → факт/формула/джерело», перелік обов’язкових додатків, обсяг підтримки та рішення щодо актуальності раунду. Якщо повна форма занадто складна для строку, явно показувати підтримувані розділи й називати результат чернеткою; не оголошувати довільний PDF готовим офіційним пакетом.

## Два паралельні потоки

**Предметний потік:** Sol збирає першоджерела/форму/зміни; людина підтверджує правила й спірні положення; Astra фіксує контракт даних. Не давати моделі самій затверджувати юридичні правила.

**Технічний потік:** Terra створює запуск, вхід, захищений профіль і deployment package. Цей потік може початися до остаточного вибору гранту. Фактичне provisioning виконується після перевірки доступу й погодження конкретних ресурсів/кошторису; дослідження цього не авторизує.

Один агент володіє bootstrap/package/lockfile. Frontend/backend паралеляться після спільної схеми API. Для незалежних змін — окремі worktrees; інтеграційні файли й документацію стану оновлює координатор. Ролі двох учасників визначаються командою, імена не призначені автоматично.

## Порядок релізів і критерії приймання

| Зріз | Конкретний результат | Перевірка завершення | Залежність |
|---|---|---|---|
| R0: skeleton | workspace, один image, frontend/API, health, env example, локальний запуск | Чистий clone запускається за README, без реальних секретів | Узгоджений стек |
| R1: auth + profile | HTTPS signup/signin/logout, власний профіль у SQL | Два акаунти; reload зберігає дані, чужий ID недоступний; є URL | GCP доступ/бюджет, R0 |
| R2: одна справа | Програма/версія джерел, confirmed facts, unknown, бюджет, revision | Одна зміна ціни правильно перераховує бюджет; стара revision дає конфлікт | B01, R1 |
| R3: AI-помічник | Opus adapter, обмежений context, пропозиції/підтвердження | Повні/неповні/суперечливі факти; немає вигаданих сум/джерел; недоступна модель не втрачає введення | Доступ/ліміт AI, R2 |
| R4: документ + export | Обмежений upload, витяг з evidence, експорт з immutable snapshot | Чужі файли недоступні; зміна справи не підміняє готовий snapshot; форма/український текст візуально перевірені | R2–R3, офіційна форма |
| R5: користувацький пілот | Люди проходять корисний сценарій | Фактичні спостереження, кількість людей, принаймні обґрунтоване рішення щодо отриманих зауважень | R1 і працездатний корисний зріз |
| R6: здача | Виправлення, run/deploy README, HTTPS URL, PDF | Кожний учасник має три артефакти з завдання; другий учасник відтворив інструкцію | R5 |

Cloud Run container повинен слухати потрібний PORT і зберігати довготривалі дані поза локальним файловим шаром. Не виконувати незавершену фонову генерацію після повернення відповіді; для довгих робіт залишається durable worker із плану. [Runtime contract](https://docs.cloud.google.com/run/docs/container-contract).

Firebase ID token перевіряється backend, з нього формується користувач; сам факт входу в інтерфейсі не захищає API. [Token verification](https://firebase.google.com/docs/auth/admin/verify-id-tokens). Worker/queue додаємо тоді, коли з’являється довга операція, разом із перевіркою повторів і відновлення; не вирізаємо recovery зі вже асинхронного сценарію заради строків.

## Пропозиції щодо обсягу до демо

Це пропозиція послідовності, а не мовчазне видалення функцій README. Широкий каталог, автоматичний моніторинг багатьох сайтів, email-підписку, підтримку всіх форматів/сканів, платіж і SFT пропоную реалізувати після першого наскрізного сценарію. Мінімальний моніторинг одного джерела можна додати, якщо основний шлях уже стабільний.

До реалізації потрібно зафіксувати, що саме команда бере в demo scope. При нестачі часу пріоритет — працюючий продукт з чесними межами, HTTPS-вхід і реальні відгуки. Заміна живого прототипу макетом не відповідає завданню. Відсутність підтвердженого open grant не дозволяє вигадати активний конкурс.

## AI-перевірка без затримки всієї розробки

Початковий технічний gate: 6–8 перевірених кейсів обраної програми — правильна відповідність, відмова за явним критерієм, unknown, суперечливі факти, змінені правила, інструкція в документі, зміна суми. Фіксуємо expected facts/evidence до запуску. Перевіряємо source support і розрахунки окремо від стилю.

Цей gate не доводить, що Opus найкращий, і не замінює [план 24-кейсового порівняння](business-legal-model-selection.md). Критичні помилки виправляємо або вимикаємо відповідну функцію; не показуємо її як перевірену. Платний прогін має точний ліміт model/tool calls і бюджет. Даних для навчання й результатів gate поки немає.

## Готові завдання для агентів наступної сесії

- **S01 / Sol, sources:** поточний раунд, форма, зміни, source manifest і карта полів. Не змінює runtime. Приймається лише з URL/версіями та явними невідомими даними.
- **T01 / Terra, skeleton/auth:** backend/frontend/infra bootstrap і запуск; один власник package/lockfile. Приймається з перевіркою реальної авторизації, ізоляції й README. До доступу GCP локальний результат не називати deployed.
- **T02 / Terra, case/budget:** після контракту S01/T01 — справа, exact money, revision і перевірки. Не змінює auth/infra без узгодження.
- **T03 / Terra, assistant/export:** після T02 — model adapter, pending proposals, snapshot export; окремий reviewer перевіряє права/суми/джерела. Не призначати ту саму людину чи агента одночасно власником конфліктних файлів.
- **Astra / integration:** призначення власників, review diff, перевірки інтеграції, зміст PR і актуальні STATUS/WORKLOG. Результат агента без перевірки не означає готовий release.

Команда паралельно готує тестувальників і згоду на використання відгуків. У цій сесії нікого не запрошували й повідомлень третім особам не надсилали. Кількість користувачів та цитати в PDF будуть фактичними.

## Найближчі невизначеності

Перша програма/раунд і форма; GCP project/IAM/billing та модельний доступ; конкретний бюджет; доступні години й власники задач; доступ до людей для пілота. Перші два потоки можуть рухатися паралельно. Додатковий research має завершуватися конкретним рішенням або зафіксованою невідомою, а не нескінченним розширенням плану.
